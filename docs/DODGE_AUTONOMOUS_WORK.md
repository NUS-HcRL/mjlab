## 2. 当前任务背景：必须核对，不能当作机器上的事实

最近讨论的任务名是 `Mjlab-Falling-Flat-PM1-AMP-Dodge`，分支为 dodge。最近已确认的方向：

- 训练只施加初始机器人朝向前方 ±30° 的水平推力；方向固定在 reset 的 yaw 坐标，不追随之后转身。
- 站立与 forward_walk reset 各约 50%；仅使用普通前摔、前摔左躲、前摔右躲三条 AMP 参考。
- 地面区域是虚拟圆，reset 时第一帧可见，生成后世界坐标固定；当前距离初始 base 为 1～2 m，半径 0.08～0.14 m，出现概率 0.5。
- 观测为 active、相对位置 xyz、radius，共 5 维，3 帧历史后 15 维。
- 不再为生成区域等待推力结束或精确预测肢体落地。用户偏好简单、提前、有效的生成方法。
- 期望区域位于自然前摔后躯干到头部可能落到的位置，不应主要放在脚下，也不能放得太远以致没有威胁。
- 已移除 dodge 的普通接触力硬终止，保留软接触力奖励和 nonfinite/invalid-physics 保护。
- 之前 play 使用不同于训练的推力，用户曾要求暂不修改 play。评估应另用训练配置，不能偷偷用默认 play 来验收。
- 用户撤回了上一版配对测试脚本。应重新检查文件、设计和实现测试，不要宣称已有完整测试基础。

此前实测参考（只作历史背景，不能替代这台机器的新数据）：

| run | 观察 |
| --- | --- |
| dodge11 / g10qun81 | 后期出现 NaN 与大量异常结束，低接触率失去意义 |
| dodge12 / 9sekt72c | 数值稳定，但末段约 61% 超力提前结束；接触率约 2% 不能证明躲避 |
| dodge13 / 0lnebsdh | 回合跑满 5 秒；接触率末段约 10.4%；势函数奖励正值不等于成功 |
| dodge15 / gpsfbxbg | 前向任务；约 2 万轮；区域出现率 49.9%，接触率约 7.1%；最终阶段先改善后停滞；左肘接触统计明显高于右肘 |

经验：

1. 低碰撞可能是区域放错、根本没摔倒、固定侧倒、检测漏报或提前结束，不一定是主动躲避。
2. 不能因奖励曲线平滑或均值增加就加长训练；末段奖励上升可能来自 AMP。
3. `gamma * Phi(next) - Phi(current)` 是势函数塑形。Phi 不变且为负时仍可能有小额正值，不能当成功奖励；其累计值也不能直接当作躲避质量。
4. 奖励项绝对值占比不是梯度占比；有效 style 与净 task 的比值受正负抵消影响。
5. 固定向某侧倒可能同时降低接触力和区域接触，但没有条件控制能力。
6. 接触传感器控制频率采样、槽数量、link 原点与真实碰撞几何差异都可能污染指标。
7. 旧 KL 公式曾记录负值，应检查数值稳定实现后再依赖 KL 早停；不要机械套用旧调参建议。
8. 课程阈值可能按环境控制步而非 PPO 迭代计数；根据实际 `num_steps_per_env` 换算。不能把源码里写的 32 当作实际一定是 32。

## 3. 先建立可持续执行的基础

MD 本身不会让 Codex、训练进程或邮件持续运行。先落实下列机制，再宣称“已进入自动工作”。

- 记录仓库绝对路径、分支、commit、dirty diff、GPU/显存、驱动、Python/依赖、磁盘余量。
- 核实训练入口、已有本地 checkpoint、reset 数据和 AMP 参考文件。优先使用现有训练环境，不随意升级核心依赖。
- 建立独立实验分支或工作目录，尊重已有用户改动；训练期间不修改该轮的源码快照或配置。
- 一张可用 GPU 默认只运行一个训练/大规模评估作业，不与用户其他作业抢占。不创建无上限的并行搜索。

- 不自动删除原始数据和历史最佳 checkpoint。磁盘不足时停止新增长作业并报告。

### 3.2 监督器与状态机

训练应运行在能在 agent 单次回合结束后存活的进程管理机制中，而不是依赖一次长时间工具调用。把“训练进程是否运行”与“Codex 当前回合是否结束”分开处理。

要求：

- 状态至少包括 BOOTSTRAP、CALIBRATING、TRAINING、EVALUATING、DIAGNOSING、PATCHING、VALIDATING、COMPLETE、BLOCKED。
- 使用原子写入和锁，保存 PID、进程启动时间、GPU、run ID、最近日志时间、阶段、下一动作、最后邮件状态。重启后先检查原进程，避免重复训练。
- 每 10～15 分钟做一次轻量监督；训练完成或失败后及时触发分析，而不是等到第二天。
- Codex 需要分析或编辑时再触发一轮 agent 工作，不用持续消耗推理资源轮询日志。

- 若调度/认证不足以持续运行，明确报告能力缺口；不要声称离线、关闭应用或电脑关机后仍保证执行。

## 4. 本地数据为主，不把 W&B 下载作为前置步骤

本机训练时直接读本地原始数据。W&B 可继续作为可选备份，不作为分析的依赖。

- 检查现有 logger。项目支持 TensorBoard，训练入口通常写 `params/env.yaml`、`params/agent.yaml`，但必须验证实际产物。
- 本地必须有全部关键 scalar、配置快照、stdout/stderr、进程退出码、checkpoint、训练 iteration 与控制步映射。
- 使用 TensorBoard event reader 或另外写本地 JSONL；读入后导出统一 analysis.json/metrics 表。处理断点重训产生的重复 step、重启边界、日志未 flush 和损坏尾记录。
- 不用网页抓取，也不把本地 `.wandb` 文件误当作普通 JSON；已有完整本地日志时不再从 W&B 拉取。
- 本地分析保留非有限值及其首次出现位置。严禁过滤 NaN 后把早期健康数据冒充末段。
- 正常小体量 scalar 用完整历史；轨迹可有选择地保留，不要求每个环境每步全量写盘。
- logger 切换必须验证 AMP/PPO 的 Debug、Train、Episode_Reward、Episode_Termination、Metrics 都能落盘，不能因禁用 W&B 丢掉关键指标。
- 安全读取 YAML，不对含任意 Python 对象标签的配置执行不可信构造；必要时新增机器可读 JSON 配置快照。

最低分析内容：

- PPO：ratio mean/std、actor grad norm、KL（核实公式）、noise std、value/policy loss；检查突然尖峰和梯度裁剪。
- AMP：policy/expert prediction、两侧 accuracy、AMP loss、grad penalty、原始/有效 style reward、style std、mix scale、task scale。
- 任务：原始/有效 task reward、各 reward 分量、回合长度、真实终止原因、接触力原始与归一化统计。
- Dodge：请求/激活率、按回合精确汇总的 hit rate、接触时间、首次 hit 时刻、碰撞部位、初始重叠、是否真正落地。
- 系统：GPU 利用/显存/温度、主存、磁盘、进程返回码、最后 checkpoint/日志时间。性能只在解释异常或效率问题时展开。

训练日志中 reset-batch 均值不能直接充当评估中的 episode-weighted 比率。缺失指标就补 instrumentation，不编造推断。

## 5. 在开始反复长训前，先建立可信评估

允许先运行小规模仿真和短训练验证工具；不允许在碰撞检测、配对恢复都未验证时连续消耗多轮长训。

### 5.1 三套场景，禁止边验收边降低难度

1. **生成器校准集**：用于设计简单、真正有威胁但可避开的区域生成方法。
2. **开发评估集**：用于每轮比较 checkpoint、定位失败、决定下一改动。
3. **最终留出集**：固定生成器版本、场景分布、独立 seed 列表和判定器版本，不用于挑参数；只在候选达标后验收。

参数和种子在训练前存档。最终留出集反复被用来调参后就不再是留出集，必须启用预留新种子，并保留旧结果。

### 5.2 验证区域生成合理：这是必过关卡

冻结一份“能正常前摔但未充分学会看区域躲避”的基线模型，不随着最新策略更新它。
优先用较早 checkpoint；另用成熟模型屏蔽区域观测作为辅助对照。后者有分布偏移风险，不独自作为结论。零动作/随机动作只能校验几何，不能作为唯一的未学习基线。

对基线记录真实碰撞几何接触点、躯干/头部落地位置、落地时间与推力/初始状态。检查：

- 前方 1～2 m 不一定就是落地范围，身高 1.4 m 也不能推导水平飞行距离。
- 未学习基线应在大量有效前摔场景中碰到区域，而不是从一开始就自然避开。
- 区域不能初始压住脚或身体，也不能大到整个可达落地区域都被覆盖。
- 在保持相同初始状态和推力时，至少通过左右躲避参考动作、可行的受控策略或已知较好策略找到安全落地证据；这只是可行性检查，不要求把 oracle 加进训练。
- 记录碰撞发生部位，确认目标覆盖用户关注的躯干到头部落地走廊，而不是主要诱导脚踩区域。

**初始工程目标**：校准集上，冻结未学习基线的有效前摔区域接触率为 30%～70%；≥90% 的校准挑战场景真正发生相关非脚部落地；初始区域重叠率为 0。
这些是本计划给出的默认目标，不是历史已实现的结果。超过 70% 不自动判定无效，但必须额外证明可避开；低于 30% 不能直接宣称任务已成功。
如果找不到满足这些条件的简单生成器，先继续校准和可行性分析，不开始下一轮大训练，也不偷偷降低门槛。

优先生成器形式：reset 时，在初始 yaw/推力坐标系中采样一个圆；距离可以是常数区间，或初始前向速度、预计冲量的一阶函数加小扰动。通过离线接触点数据拟合系数/区间，最多少量可解释分段。

不要优先恢复“推完再等几帧，再按瞬时肢体自由落体预测”的延迟生成方式。不要用当前训练中策略的未来轨迹实时追着放区域。生成时只能使用 reset 时已有的信息。

允许根据证据调整距离、偏角、半径、概率和推力课程，但每次生成器变更必须：

1. 版本化参数与代码；重跑冻结基线的碰撞率和可行性检查。
2. 让旧 best 与新候选在同一个新版本开发集上重测。
3. 保留旧固定评估集的回归结果，不能混用不同难度分布的成功率。
4. 禁止通过降低出现概率、把区域移远、缩小至几乎不可能撞到等方式获得虚假进步。

### 5.3 配对测试：确定策略确实使用区域信息

在训练配置下实现独立 evaluator，不依赖当前 play 的不同推力。默认开发评估 256 组起步；左右各一次。

- 每对使用完全相同的 qpos/qvel、动力学参数、推力向量/持续时间、区域距离/半径和观测历史初始化；只改变区域左右位置。
- 关闭观测噪声、使用 deterministic actor；完整加载观测归一化。严格检查 checkpoint 结构，不静默忽略缺失权重。
- 保留用于测试的碰撞和安全保护；在自动 reset **之前**抓取终止帧，不把 reset 后姿态记为落地。
- 清空外力、求解器 warmstart、动作/history、状态型 reward/command、pulse timer 等，避免前次回合污染。
- 先做“完全相同条件重复两次”的负对照，估计 GPU 仿真数值差异。实际左右响应必须明显超过此噪声基线。
- 记录 active/initial overlap、实际落地、首次接触、身体部位、region hit、接触时间、姿态旋转、躯干横移和动作差异。
- 记录区域可见后 0.2/0.5/1.0 s、首次相关接触时及回合结束的状态，区分落地前躲避与落地后挪动。
- 全身真实接触用于碰区域判定，不能因为 reward 未包含 head 就把头部碰区域排除。
- 接触检测至少与训练一致；独立评估尽可能使用子步接触累计或完整 MuJoCo 接触校验，检查四槽截断和控制频率漏检。若暂不能消除漏检，量化误差，不将该检测器作为最终近零碰撞的唯一依据。

主要解释：障碍换边后，机器人是否在落地前以合理方向改变侧移、旋转或肢体动作？动作改变后是否真的降低碰撞？
3 cm 配对横移差可作为初步可视化阈值，但不能把它硬当成功标准；纯旋转/收臂也可以躲。固定侧倒不合格。

### 5.4 数据分母与统计

- 分开报告全部 requested/active 场景、真实落地场景、冻结基线本来会碰撞的挑战子集。
- 未落地、异常终止、初始重叠、检测不可靠的场景必须单列，不能从分母悄悄删除后报告“成功”。异常结束不能算成功。
- 对“冻结基线会撞、候选避开”的相同挑战场景报告挽救比例；同时报告候选新引入的碰撞。
- 按推力强度/持续时间、站立或前行初态、区域距离/侧别、接触部位分层。
- 使用按基础场景聚类的配对 bootstrap 或适当的二项比例区间，不把同一场景左右/重复轨迹当作完全独立样本。
- 保存 CSV/JSON、场景与模型 hash、选定轨迹 NPZ、关键成功和失败视频。视频要覆盖固定侧倒、左右对应躲避、非摔倒和强推力失败，不只挑成功案例。

## 6. “理想效果”的默认验收标准

下面是对用户定性要求的**操作化默认标准**。启动时写入 acceptance.json 并冻结；可以增加更严格检查，不得为了结束任务自动降低标准。若发现不合理，列证据请求用户调整，而不是自己宣布成功。

同时满足：

1. **生成器有效**：冻结基线在同一分布上满足第 5.2 节威胁与初始无重叠要求；有可避开的证据。
2. **几乎不撞**：候选在锁定留出挑战集上的真实区域接触率 ≤1%，95% 置信上界 ≤2%；全体有效区域场景也报告相同指标。至少 3 个独立环境 seed、每个 512 个基础场景起步；若挑战子集太少或区间太宽，补样本，不能报 0/几个就达标。
3. **没有靠不摔/异常逃避**：挑战集相关落地率 ≥90%；invalid/nonfinite 率 ≤0.1%，非有限模型参数/训练损失为 0。未落地另列，不折算成躲避成功。
4. **区域条件响应**：有超过同条件重复噪声的、方向/几何上合理的落地前响应，并在冻结基线会撞的配对场景显著改善真实接触。横移、旋转、肢体调整均可，不能用单一横移门槛排除有效策略。
5. **dodge 回报显著提升**：用固定 evaluator、固定权重与同一场景重新评分。核心碰撞/成功相关分量相较冻结基线显著改善（配对 95% 区间不跨零），并与真实接触结果一致。训练 reward 配方变了就重新评分全部候选，不能直接比较不同权重的训练曲线；势函数正值不能单独满足该条。
6. **可复现**：候选在另一独立训练 seed 的确认训练/合理复现实验中仍能达到上述实质目标，不靠挑中一个偶然 checkpoint。昂贵确认只对通过开发验收的最佳方案做。
7. **动作范围合理**：没有依赖离开任务区域、异常高速、求解器漏洞、持续蹦跳或落地后大幅爬行。记录躯干运动范围、头/躯干冲击分布、关节/力异常；即便未设置普通力硬终止，也不能忽视严重退化。

满足前不要宣称“已学会”；满足后冻结 best，输出可复现评估包，停止继续训练和自动改代码，发送最终结果邮件，然后停止周期任务。

## 7. 每轮工作的完整闭环

### A. 先解释当前结果

每轮结束必须同时看全程、末段、课程切换前后及多个 checkpoint，写 diagnosis.md：

- 本轮假设是什么，证据支持还是反驳？
- 不足来自区域无威胁/过难、条件信息未使用、reward 错位、AMP 牵制、PPO 不稳定、reset/推力分布还是检测/实现错误？
- 哪些是观察事实、哪些是推测、还缺哪个实验？
- 本轮相比共同基准是否改善？有无以普通摔倒退化换取表面收益？

不得只看平均奖励、列一两个泛泛建议就开始下一轮。

### B. 先做便宜的判别实验

优先做固定 checkpoint 的区域扫描、配对恢复校验、传感器交叉检查、短仿真、奖励离线重算、针对性消融。
必要时录制关键视频；不要用文字猜测替代已具备条件的实测。
有些问题无需训练即可确定，例如区域几乎从不覆盖接触点、终止帧记录错误、负 KL 数值问题。

### C. 基于证据设计下一轮

写 experiment_plan.md，至少包含：证据、主要因果假设、准备改的文件/参数、预期可观测变化、验证集、失败判据、资源预算与回滚点。

“深入分析”不等于一次随机改十个参数。围绕一个主要机制可以做一组必要改动；使用最小能验证假设的实验，避免无法归因。
权重调整不是被禁止，但必须有固定评估和机制证据，不能成为默认的唯一行动。

可自主选择的改进方向：

- 简化并校准前方目标区域；按初态/冲量做少量可解释分段。
- 修正 reward 与真实碰撞/落地目标不一致，处理首帧、terminal、time limit、dt 和重复获奖。
- 改善 actor 可见信息及归一化/history，验证其实际送入网络而非只存在于 cfg。
- 调整 AMP 参考采样和混合，检查有效 task/style，而不是只改名义权重。
- 分阶段难度/威胁概率课程，但固定验收集不变。
- 必要时修改 PPO 稳定性、训练长度、初始化或网络；没有证据不默认扩大网络。

### D. 验证后再训练

1. 编译/静态检查、相关测试。
2. 8～32 个环境的实际 smoke：至少完整跨 reset、pulse 开始/结束、首次接触、异常/timeout。
3. 约 300～1000 迭代的短训练，确认指标、checkpoint、归一化和 evaluator 可用。
4. 再进入正式训练，优先用当前吞吐估算 GPU 小时。短训不能证明最终质量；不能在强推力课程尚未开始时以低接触率提前宣布成功。
5. 定期 checkpoint，建议约每 1000～2000 迭代且保留 last、best、关键课程点；避免反复全量高开销评估。

训练命令先用本地 --help 核实。若与当前接口相符，可采用以下结构，不直接照抄未经核实的恢复参数：

```bash
uv run train Mjlab-Falling-Flat-PM1-AMP-Dodge --agent.logger tensorboard
```

改变观测维度、模型结构、归一化或奖励尺度时，核实 checkpoint/optimizer 的兼容性。需要重新训练就明确记录；不要静默部分加载或盲目恢复旧 optimizer。不要恢复 NaN checkpoint。

### E. 选择下一动作

- 同分布有效评估持续改善、尚未达到平台：有依据地继续当前训练，不强行为了“改进”改代码。
- 平台/退化：回到分析和判别实验，再制定新的实验。
- 数值错误/碰撞检测错误/数据缺失：先修工具或实现，不继续烧长训。
- 连续 3 个正式候选没有可验证进步：暂停新的长训，做系统性失败分析和更强对照；可继续低成本研究，不把这种情况伪装成“仍在正常优化”。

## 8. 资源、异常与失败恢复

- 每轮 launch 前检查 GPU 占用、显存和磁盘；预计剩余日志/checkpoint 空间不足则不开新作业。
- 日志超过正常间隔多倍不更新时，同时检查进程、GPU、stdout 和是否正在保存/编译。不能仅因短暂无 scalar 就杀进程。
- OOM 可降低环境数或评估批量；降低环境数会改变统计/吞吐，记录配置变化。
- 出现 NaN、异常物理激增、GPU 错误时先保存诊断与最近正常 checkpoint，再停止自己的失败进程。禁止直接 nan_to_num 掩盖根因后宣称修好。
- 同一异常最多自动重试 2 次；之后转诊断，避免无限重启。机器/账户/权限故障无法修复则 BLOCKED 并报告明确所需信息。
- 检查内核/OOM/GPU 日志须遵守访问权限；无法读取就记录未知，不能断言“电脑死机”。
- 长训练停机不要简单依靠 finally 保存：尽可能实现可控停止与原子 checkpoint。恢复前检查文件完整性与来源。
- 不固定无限迭代计划：每轮有明确迭代/时间上限和评估门槛，但用户未停止且未达标时，可以继续下一轮有根据的实验。
